## 7.2 三层许可：代码、权重、数据

这是最容易踩坑的地方。一个“开源人脸项目”通常有三层许可：

1. **代码许可**：GitHub 仓库的 LICENSE，常见 MIT/Apache/GPL；
2. **模型权重许可**：预训练权重往往单独声明“仅限研究”，例如 InsightFace 模型库明确写明 ALL models are available for non-commercial research purposes only；
3. **训练数据许可**：MS1M、Glint360K、WebFace600K 等数据集通常只允许研究用途，用它们训练出的商用模型也可能受约束。

因此，“代码 MIT”不等于“可以商用”。商用前要逐项确认：代码、权重、数据、以及是否包含第三方专利/肖像权风险。

## 7.3 两条许可路线

| 路线 | 适用 | 可用组件 | 代价 |
| --- | --- | --- | --- |
| 开源路线 | 个人项目、开源 App、研究 | YOLO（AGPL）+ InsightFace 权重 + DeepSORT | 整个项目需按 AGPL 开源；不能闭源分发 |
| 商用路线 | 闭源 App、应用商店付费 | EfficientDet-Lite0/YOLOX + 自训 MobileFaceNet/ArcFace + ByteTrack + relationship.js | 需自训模型或购买授权；成本增加 |

建议在立项第一天就确定路线，不要等产品做完再换模型。**换检测器/识别器不是“改个依赖”，而是重做数据、阈值、前后处理、回归测试。**

## 7.4 不建议直接复用的项目

| 项目 | 原因 |
| --- | --- |
| face-api.js | TensorFlow.js 在 WebView 中性能差、内存高，不适合实时相机 |
| dlib / face_recognition | 模型体积大、ARM 端慢，且 dlib 编译链复杂 |
| CompreFace | 服务端方案，与“全部本机算力”冲突 |
| OpenCV 全量 | APK 体积增加几十 MB，本项目只需要少量图像处理 |
| 各类“人脸识别 Demo App” | 多为 InsightFace 权重 + 旧版 TFLite，许可与维护性都不可控 |

# 第8章 性能、功耗与 ColorOS 适配

## 8.1 基准测试方案

不要用“感觉流畅”做验收。建议建立一套可重复的基准：

| 维度 | 方法 | 工具 |
| --- | --- | --- |
| 单模块延迟 | 固定输入，跑 100 次取 p50/p95 | 自建 benchmark Activity |
| 端到端延迟 | 相机时间戳 → 标注上屏 | Perfetto、`Choreographer` |
| 帧率 | 连续 5 分钟统计 | `dumpsys gfxinfo`、Perfetto |
| 内存 | 峰值/常驻 | Android Studio Profiler、`dumpsys meminfo` |
| 功耗/温升 | 连续 10 分钟 | Battery Historian、热成像/`dumpsys thermalservice` |
| 识别质量 | 自建家庭测试集 | 脚本统计 rank-1/FAR/FRR |
| 跟踪质量 | 标注视频 | MOTA/IDF1/IDS 脚本 |

测试集建议：20–30 人、每人 5–10 张底照；10 段真实室内视频（白天/夜晚/逆光/遮挡/多人）；距离 1/2/3/4/6/10/20 m，重点覆盖“远距只检测、近距才识别”的切换边界。

机型矩阵（只适配 ColorOS 14–17）：

| ColorOS 版本 | Android / API | 代表机型（示例） | 测试重点 |
| --- | --- | --- | --- |
| ColorOS 14 | Android 14 / API 34 | Find X7、Reno 11 | 老机型性能、CameraX/HAL 兼容、前台服务 |
| ColorOS 15 | Android 15 / API 35 | Find X8、Reno 13 | 16 KB 页对齐、edge-to-edge、权限 |
| ColorOS 16 | Android 16 / API 36 | Find X9、Reno 15 | 新 GPU/NPU、后台限制、功耗 |
| ColorOS 17 | Android 17 / API 37 | Find X10、OnePlus 16 | Android 17 行为变更、相机/权限回归 |

> 机型仅为例，实际以团队持有设备为准；每个大版本至少 1 台，最好覆盖 1 台骁龙 + 1 台天玑。

## 8.2 预估性能

以下为工程估算，实际以目标机型实测为准：

| 模块（INT8/GPU） | ColorOS 14 老机型 | ColorOS 15–16 中高端 | ColorOS 17 新旗舰 |
| --- | --- | --- | --- |
| 人体检测 320 | 20–35 ms | 10–18 ms | 6–10 ms |
| 人脸检测 640（仅 NEAR） | 30–50 ms | 12–22 ms | 8–14 ms |
| 特征提取 112（仅 NEAR） | 10–18 ms | 6–12 ms | 4–7 ms |
| 跟踪 | 1 ms | 0.5 ms | 0.3 ms |
| 远距单帧 | 25–45 ms | 15–28 ms | 10–18 ms |
| 近距单帧 | 60–100 ms | 30–50 ms | 20–30 ms |
| 远距 FPS | 22–30 | 30–40 | 40–60 |
| 近距 FPS | 10–12 | 18–22 | 25–30 |
| 常驻内存 | 180–280 MB | 150–250 MB | 150–250 MB |

注意：这是“每帧都跑”的合计。实际调度下，人体检测 8 Hz、人脸 5 Hz、特征 3 Hz，平均 CPU/GPU 占用可以降到 30–50%；远距模式不跑人脸，功耗和帧率明显更好。

## 8.3 优化手段

按性价比排序：

1. **远距不加载人脸模型**：最大收益；FAR 只跑人体 + 跟踪，进入 NEAR 再加载人脸检测/特征/匹配。
2. **量化**：FP16 几乎无损；INT8 需要校准集（500–1000 张家庭场景图），识别模型 INT8 可能掉 1–3 个点，需回归测试。
3. **降分辨率**：人体检测 320 足够；人脸检测 640 是精度/速度平衡点；不要用 4K 做检测。
4. **ROI**：只在 NEAR 模式对有人体的区域做人脸检测；多人时只处理最大/最近的 1–2 个。
5. **跳帧**：检测 5–10 Hz，跟踪每帧；识别 2–5 Hz；UI 30 FPS 插值。
6. **GPU delegate**：LiteRT GPU delegate 对卷积网络通常比 CPU 快 2–5 倍；注意 Mali 的纹理/内存限制。
7. **NPU**：高通 QNN、联发科 NeuroPilot 可进一步降耗，但需要单独适配，建议 V2 再做。
8. **零拷贝**：CameraX `ImageProxy` → GPU 纹理 → 模型输入，减少 YUV↔RGB 转换。
9. **NMS 优化**：移动端 NMS 用排序 + 提前终止；人脸检测框数量通常 < 50，影响不大。
10. **线程亲和**：推理线程绑定大核，UI 线程不参与计算；避免 GC 抖动。
11. **热管理**：监测 `PowerManager` 热状态，动态降帧；不要在高温下继续满负荷。
12. **16 KB 页对齐**：Android 15+ 对 native `.so` 的页对齐要求；ColorOS 15–17 需验证 LiteRT/NCNN 库的 16 KB 对齐，避免安装或加载失败。

## 8.4 功耗与热

目标：连续使用 10 分钟，电量消耗 ≤ 15%，机身温升 ≤ 8 °C，不触发系统降频。

措施：

- 预览 30 FPS，但分析流按需降帧；
- 屏幕亮度自适应，避免长时间最高亮度；
- 识别成功后降低特征提取频率（已识别的人不需要每帧算）；
- 无人时进入低功耗模式（人体检测 3 Hz）；
- 远距模式功耗约为近距的 50–60%，长时间看人时优先保持 FAR；
- 提供“省电模式”开关（关闭活体、降低分辨率）；
- ColorOS 的省电模式可能限制 GPU/后台，首次使用引导用户把本 App 加入“允许后台运行/不省电”名单；高性能模式只作为选项，不默认开启。

### 8.5.2 ColorOS 专项问题

| 问题 | 影响 | 对策 |
| --- | --- | --- |
| 国内 ColorOS 无 GMS | ML Kit 部分能力不可用 | 全链路用 LiteRT，不依赖 GMS |
| 前台服务相机类型 | Android 14+ 必须声明 `camera` 类型 | `foregroundServiceType="camera"` + `FOREGROUND_SERVICE_CAMERA`；引导电池/自启动设置 |
| 相册部分授权 | Android 14 只给用户选中的照片 | 处理 `READ_MEDIA_VISUAL_USER_SELECTED`；引导全量授权 |
| 16 KB 页大小 | Android 15+ 对 native 库的对齐要求 | 用最新 NDK/LiteRT；检查 `.so` 与 zip 的 16 KB 对齐 |
| Edge-to-edge | Android 15/16 强制全面屏 | Compose insets；不要硬编码状态栏高度 |
| Adreno / Mali GPU | GPU delegate 兼容性差异 | 提供 CPU 回退；按 GPU 型号白名单 |
| NPU 不开放 | MariSilicon X 等第三方不可用 | 不依赖 NPU；QNN/NeuroPilot 仅 V2 评估 |
| 应用分身/双开 | 数据目录、权限差异 | 真机测试；避免写死路径 |
| ColorOS 17 行为变更 | Android 17 新限制 | targetSdk 37 回归；关注相机、前台服务、权限 |

最低配置建议：ColorOS 14（Android 14 / API 34）、arm64-v8a、6 GB RAM；4 GB 机型只保留“拍照识别”，不做实时预览。机型覆盖目标：ColorOS 14/15/16/17 各 1–2 台，共 6–8 台，至少包含 1 台骁龙 + 1 台天玑。

| 禁止上传 | 代码审查无网络上传；无第三方统计 SDK | 抓包 + 依赖审查 |
| 加密 | 数据库 SQLCipher；照片 EncryptedFile；密钥 Keystore | 安全测试 |
| 应用锁 | 可选指纹/密码解锁 | 功能测试 |
| 删除 | 删除人即删除样本/照片/别名；清空数据二次确认 | 数据检查 |
| 撤回 | 撤回同意即停止处理并删除 | 用例测试 |
| 保留期限 | 默认长期保留，提供“自动清理 N 年未使用”选项 | 设置项 |
| 导出 | 二次确认 + 单独同意 + 加密 + 告知风险 | 交互走查 |
| 儿童规则 | 单独说明、监护人可删除 | 文档 + 功能 |
| PIPIA | 上线前完成并归档 3 年 | 文档 |
| 权限最小化 | 只申请相机/相册；不申请通讯录/定位 | 权限清单 |
| 后台 | 不在后台采集；离开页面即停 | 生命周期测试 |

## 9.4 伦理边界

技术可行不等于应该做。本项目应明确以下伦理边界：

- **不识别陌生人**：画面里的陌生人一律“未知”，不猜姓名、不猜身份、不展示年龄/性别推断。
- **不用于监控**：不做后台录制、不做远程查看、不做多人轨迹分析。
- **不侵犯隐私空间**：不在地铁、商场、洗手间等公共场所对他人使用；产品文案明确“家庭场景”。
- **尊重被录入者**：录入前告知对方；对方拒绝则删除；提供“不要识别我”的开关（把人加入排除名单）。
- **不制造焦虑**：不宣传“叫错就社死”，而是“帮你更从容地打招呼”。
- **可解释**：每个称呼都能点开看“为什么这样叫”（关系链），让用户能判断对错。

## 9.5 应用商店与上架材料

## 9.6 数据泄露与丢失应对

- **手机丢失**：数据库加密 + 应用锁 + 生物识别；不提供云端找回；建议用户远程擦除设备。
- **导出包泄露**：AES-GCM + 口令；口令强度提示；导出包内不含原始照片（可选）。
- **误删除**：提供“最近删除”7 天（本地加密），但撤回同意/删除人时不保留。
- **日志**：不记录人脸、embedding、姓名到 logcat；崩溃日志脱敏。
- **截图**：可选 `FLAG_SECURE`；但用户可能想截图分享，默认不开启。

> **底线：** 这个 App 的信任基础是“数据不出手机”。任何一次云端上传、广告 SDK 上报、系统自动备份，都会摧毁这个信任。产品/工程/法务必须在这条线上达成一致。
