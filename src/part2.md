# 第4章 系统架构设计

## 4.1 总体架构

系统分为五层：采集层、感知层、认知层、数据层、交互层。与用户提出的“目标检测 + 目标跟踪 + 人脸识别 + 数据库”相比，多了“认知层（关系推理）”和“录入/校准”两条贯穿线。

![图 1 端到端系统架构](assets/fig1_architecture.png)

| 层 | 模块 | 职责 | 关键技术 |
| --- | --- | --- | --- |
| 采集层 | CameraX / 相册选择 | 取流、对焦、曝光、缩放、YUV 输出 | CameraX、ImageAnalysis、STRATEGY_KEEP_ONLY_LATEST |
| 感知层 | 预处理 | YUV→RGB、缩放、ROI 裁切、归一化 | libyuv、GLES shader、NEON |
| 感知层 | 模式调度 | 按人体框高度切换 FAR/NEAR，控制人脸模型加载 | 状态机 + 滞回 |
| 感知层 | 人体检测 | 远距/近距都运行；远距主任务，输出 person box | EfficientDet-Lite0 / YOLOX-Nano |
| 感知层 | 多目标跟踪 | 维持 track ID，处理遮挡与丢失 | ByteTrack（Kalman + Hungarian） |
| 感知层 | 人脸检测 | 仅近距模式；在 person ROI 内找脸，输出 5 点 | SCRFD-2.5G / MediaPipe |
| 感知层 | 对齐与质量 | 仅近距；仿射到 112×112，质量打分 | 5 点相似变换、Laplacian、姿态估计 |
| 感知层 | 特征提取 | 仅近距；输出 512 维 embedding | MobileFaceNet / ArcFace |
| 认知层 | 人脸匹配 | 仅近距；1:N 开集匹配，输出身份与置信度 | 余弦相似度、top-1 + margin |
| 认知层 | 身份融合 | 跨帧投票、track 与 face 绑定 | 时序平滑、track-level voting |
| 认知层 | 关系推理 | 由关系图计算称呼、补全未知关系 | BFS + 规则引擎 + relationship.js |
| 数据层 | 本地数据库 | 人、关系、样本、别名、同意记录 | Room + SQLCipher |
| 数据层 | 文件存储 | 加密照片、导出包 | EncryptedFile、AES-GCM |
| 交互层 | AR 标注 | 人头上方显示称呼/置信度 | Custom View / Compose Canvas |
| 交互层 | 详情与编辑 | 关系链、照片、纠正 | Compose |
| 交互层 | 语音播报 | “三姨，新年好” | Android TextToSpeech |
| 交互层 | 录入向导 | 关系链选择、批量导入 | 向导式 UI |

## 4.2 远/近两档状态机

级联的核心不是“距离”，而是“当前模式是否需要人脸模型”。远距模式完全不加载人脸检测/识别；近距模式才加载。工程上用人体框占画面高度的比例作为远近代理指标：

![图 2 远/近两档状态机](assets/fig2_state.png)

| 状态 | 判定条件（参考值） | 运行模块 | 界面表现 |
| --- | --- | --- | --- |
| FAR | 人体框高 < 65% 画面高（约 >4 m） | 人体检测 + 跟踪；人脸模型不加载 | 灰色人形框，显示“有人” |
| NEAR | 人体框高 ≥ 65%（约 ≤4 m） | 人体检测 + 跟踪 + 人脸检测 + 质量 + 特征 + 匹配 | 绿色/黄色框 + 称呼 |
| IDENTIFIED | 连续 3 帧匹配一致，且相似度 ≥ 阈值 | 跟踪 + 匹配 | 稳定显示称呼与关系链 |
| UNCERTAIN | 匹配到但 margin 不足，或质量低 | 匹配 + 候选生成 | 显示 top-3 候选，点击确认 |
| LOST | 连续 30 帧无检测，或目标离开画面 | 跟踪预测 | 框淡出，保留 2 秒轨迹 |

设计要点：

- **滞回**：FAR→NEAR 用 65%，NEAR→FAR 用 55%（约 4.0 m / 4.7 m），避免人在边界来回走导致状态抖动。
- **远距不跑人脸**：FAR 只跑人体检测 + 跟踪，不加载人脸模型；这是本产品与“全程人脸识别”方案最大的算力/功耗差异。
- **近距才识别**：进入 NEAR 后，人脸宽 ≥60 px 且质量合格才做特征与匹配；≥80 px 更稳。
- **不承诺远距识别**：FAR 只显示“有人”，不显示姓名；用户可点“识别”强制进入 NEAR（例如人还远但想试）。
- **多目标**：每个 track 独立状态机；画面里 5 个人时，只对最近/最大的 1–2 个进入 NEAR，其余只跟踪。
- **阈值需标定**：65%/55% 是 1080p、60° 视场下的经验值；不同焦段、分辨率、屏幕比例要重新标定。

## 4.3 帧调度与线程模型

实时管线最怕“某一帧卡住，后面全排队”。远距模式（FAR）只跑人体检测、跟踪、渲染；近距模式（NEAR）才加入人脸检测/特征/匹配。推荐如下调度：

| 任务 | 模式 | 频率 | 线程 | 输入分辨率 | 备注 |
| --- | --- | --- | --- | --- | --- |
| 相机预览 | 全部 | 30 FPS | CameraX | 1080p | 只做显示 |
| 分析流 | 全部 | 30 FPS | CameraX Executor | 1280×720 | KEEP_ONLY_LATEST，丢旧帧 |
| 人体检测 | FAR + NEAR | 8–10 Hz | GPU/CPU 推理线程 | 320×320 或 416×416 | 每 3 帧一次 |
| 跟踪 | FAR + NEAR | 每帧 | 轻量线程 | — | < 1 ms |
| 人脸检测 | 仅 NEAR | 5–8 Hz | 推理线程 | 640×640（ROI 可降到 320） | 仅对 NEAR 的 track |
| 特征提取 | 仅 NEAR | 2–5 Hz | 推理线程 | 112×112 | 仅对质量合格的 face |
| 匹配/关系 | 仅 NEAR | 2–5 Hz | 推理线程 | — | 连续 3 帧稳定 |
| UI 渲染 | 全部 | 30 FPS | 主线程 | — | 只读最新结果，不阻塞 |

关键原则：

1. **分析流与预览流分离**：预览用高分辨率保证观感，分析用 720p 保证吞吐；不要把 4K 帧直接送进模型。
2. **只保留最新帧**：`STRATEGY_KEEP_ONLY_LATEST` + 背压丢弃，避免延迟堆积。
3. **推理结果异步发布**：用 `StateFlow`/`AtomicReference` 发布“最新检测结果”，UI 拿不到新结果就沿用上一帧的框，不要等待。
4. **ROI 只在 NEAR 用**：进入近距模式后，人体框扩大 1.5 倍作为人脸检测 ROI；FAR 模式不做人脸 ROI，也不加载人脸模型。
5. **双缓冲**：相机帧、模型输入张量各用双缓冲，避免 GPU/CPU 竞争。

## 4.4 延迟预算

以 ColorOS 15–16 的中高端机（骁龙 7 系 / 天玑 8000 系）为目标，单帧预算如下（工程估算，需实测）：

| 阶段 | 远距 FAR（ms） | 近距 NEAR（ms） | 说明 |
| --- | --- | --- | --- |
| 采集 + 预处理 | 4–8 | 4–8 | GPU shader 可压到 3–5 |
| 人体检测 320 INT8 | 10–18 | 10–18 | GPU delegate |
| 跟踪 | < 1 | < 1 | 20 个 track |
| 人脸检测 640 INT8 | — | 12–22 | 仅 NEAR |
| 对齐 + 质量 | — | 2–4 | 仿射 + 拉普拉斯 |
| 特征提取 112 INT8 | — | 6–12 | MobileFaceNet |
| 匹配（300 模板） | — | < 1 | 暴力余弦 |
| 关系推理 | — | < 1 | 图缓存 |
| 渲染/标注 | 2–4 | 2–4 | 主线程 |
| **单帧合计** | **20–35** | **40–70** | 按需调度，不是每帧全跑 |
| **端到端（预览→标注）** | **50–90** | **80–150** | p95 ≤ 150 ms |
| **可持续 FPS** | **25–30** | **15–20** | 中端机 |

远距模式因为不跑人脸模型，功耗和帧率明显更好；把“远距限定为检测+跟踪”不仅是产品约束，也是工程收益。

## 4.5 降级策略

| 场景 | 降级动作 |
| --- | --- |
| ColorOS 14 老机型 | 分析流降到 640×480；人体检测 5 Hz；人脸检测 3 Hz；关闭活体 |
| 热降频 | 动态降帧；优先保证“检测 + 跟踪”，暂停特征提取 2 秒 |
| 远距模式 | 默认不加载人脸模型；只有进入 NEAR 才加载，离开后可释放或保留缓存 |
| 多人场景（> 5 人） | 只识别画面中央/最大的人脸；其余只跟踪 |
| 人脸质量差 | 不识别，显示“看不清，靠近一点”；保留 track |
| 模型加载失败 | 回退到 MediaPipe/ML Kit 轻量检测；关闭识别并提示 |
| 电量低 | 提示并降低帧率；不做后台运行 |

# 第5章 关键算法与模型选型

## 5.1 人体检测：远距离“发现有人”

人体检测是远距模式的主任务，也是近距模式的第一级检测；两档都运行，但远距不触发人脸模型。人体检测的任务不是识别，而是在 10–20 m 外稳定发现“画面里有人”，并给出可用于跟踪的框。选型原则：**许可干净、模型小、对小人形召回好、易于转 TFLite。**

| 模型 | 输入 | 参数量/体积 | 许可 | 优点 | 缺点 |
| --- | --- | --- | --- | --- | --- |
| EfficientDet-Lite0 | 320×320 | 约 3–4 M / 4.4 MB | Apache-2.0 | MediaPipe 直接支持，集成最快 | 小目标一般 |
| EfficientDet-Lite2 | 448×448 | 约 7 MB | Apache-2.0 | 精度更好 | 延迟明显上升 |
| YOLOX-Nano | 416×416 | 0.91 M | Apache-2.0 | 精度/速度均衡，社区活跃 | 需自己转 TFLite/NCNN |
| NanoDet-Plus-m | 416×416 | 约 1.2 M | Apache-2.0 | 超轻，适合低端机 | 小目标与遮挡较弱 |
| PP-YOLOE-s | 640×640 | 约 7.9 M | Apache-2.0 | 精度高 | 体积/延迟偏大 |
| YOLOv8n / YOLO11n | 640×640 | 3.2 M / 2.6 M | **AGPL-3.0** | 生态最好，教程最多 | 闭源商用需企业授权 |

**推荐：** MVP 用 EfficientDet-Lite0（MediaPipe Object Detector 直接可用，Apache-2.0，零许可风险）；如果小目标召回不够，再换 YOLOX-Nano 或 NanoDet-Plus。**不建议**在闭源产品中直接使用 Ultralytics YOLO 系列，除非购买企业授权或整个项目开源。

远距离小目标的工程手段：

- 输入分辨率从 320 提到 416/512，比换更大模型更划算；
- 对画面做“中心优先”调度：画面中央 60% 区域全分辨率检测，边缘降采样；
- 每 2–3 秒做一次全图高分辨率检测，弥补逐帧低分辨率的漏检；
- 利用运动信息：连续帧差分/光流给出“可能有人”的区域，再送检测器。

## 5.2 人脸检测：近距离“找到脸”

人脸检测只在近距模式（NEAR）启用；远距模式不加载该模型，避免无谓算力与功耗。

| 模型 | 输入 | 参数量/体积 | 许可 | 优点 | 缺点 |
| --- | --- | --- | --- | --- | --- |
| MediaPipe BlazeFace short-range | 128×128 | 约 0.2 MB | Apache-2.0 | 极快，2 m 内效果好 | 小脸/远距弱 |
| MediaPipe BlazeFace full-range | 192×192 | 约 1 MB | Apache-2.0 | 5 m 内可用，集成简单 | 侧脸/遮挡一般 |
| ML Kit Face Detection | 自适应 | 随 Play Services | Google 条款 | 快、稳定、带轮廓/跟踪 ID | 无 embedding；国内 ColorOS 无 GMS 不可用 |
| SCRFD-500M | 640×640 | 0.57 M / 约 2.5 MB | 代码 MIT；**权重非商用** | 小脸召回好，5 点关键点 | 需转换；权重许可需处理 |
| SCRFD-2.5G | 640×640 | 0.67 M / 约 3 MB | 代码 MIT；**权重非商用** | 精度/速度平衡最佳 | 同上 |
| RetinaFace-m025 | 640×640 | 约 0.44 M | 代码 MIT；权重非商用 | 成熟稳定 | 后处理较重 |
| YuNet | 320×320 | 约 0.1 MB | MIT（OpenCV Zoo） | 极轻，许可干净 | 小脸/侧脸弱于 SCRFD |

SCRFD 在 WIDER FACE 上的公开数据（单尺度、VGA）如下，可作为“精度/算力”权衡依据：

| 模型 | Easy | Medium | Hard | FLOPs | 参数量 |
| --- | --- | --- | --- | --- | --- |
| SCRFD-500M | 90.57 | 88.12 | 68.51 | 500 M | 0.57 M |
| SCRFD-2.5G | 93.78 | 92.16 | 77.87 | 2.5 G | 0.67 M |
| SCRFD-10G | 95.16 | 93.87 | 83.05 | 10 G | 3.86 M |

**推荐：** 如果接受 InsightFace 权重许可（或自行训练/购买授权），选 SCRFD-2.5G：Hard 集比 500M 高约 9 个百分点，算力只多 5 倍，仍然适合移动端。若必须许可干净，选 MediaPipe Face Detector full-range + YuNet 兜底；代价是远距离小脸召回下降，需要用“走近再识别”的产品设计弥补。

> **重要提醒：** “代码 MIT”不等于“模型权重可商用”。InsightFace 模型库明确写明所有模型仅限非商业研究。SCRFD、RetinaFace、buffalo 系列的权重都受此约束；商用前必须替换为自有训练权重或取得授权。

## 5.3 人脸对齐与质量评估

对齐：用 5 点（双眼、鼻尖、嘴角）做相似变换，裁到 112×112（ArcFace 标准）。对齐质量直接决定 embedding 质量，务必在 App 内实现，而不是把整张图直接送进识别模型。

质量评估建议至少包含：

| 指标 | 方法 | 合格线（参考） | 不达标处理 |
| --- | --- | --- | --- |
| 人脸尺寸 | 检测框宽度 | ≥ 60 px（识别）；≥ 40 px（检测） | 提示靠近 |
| 模糊 | Laplacian 方差 | ≥ 50（归一化后） | 提示稳定 |
| 姿态 | 5 点估计 yaw/pitch | yaw ≤ 30°，pitch ≤ 20° | 提示正脸 |
| 亮度 | 平均灰度/直方图 | 50–200 | 提示补光/避逆光 |
| 遮挡 | 关键点可见度/分割 | 眼鼻口可见 | 提示摘口罩/眼镜反光 |
| 表情 | 可选 | 中性或微笑 | 不作为硬门限 |

策略：**低质量样本不进库，但可以进跟踪。** 近距识别前严格把关，识别时宽松（低质量只显示“看不清”，不强行匹配）。

## 5.4 人脸识别：从“脸”到“身份”

人脸识别只在 NEAR 模式运行；FAR 模式不加载特征提取与匹配模型。

### 5.4.1 模型选型

| 模型 | 骨干 | 体积 | 算力 | LFW | 东亚人脸（InsightFace 评测） | 许可 |
| --- | --- | --- | --- | --- | --- | --- |
| MobileFaceNet（WebFace600K） | MobileFaceNet | 13 MB | 450 M FLOPs | 99.70 | 51.03 | 权重非商用 |
| ArcFace R50（WebFace600K） | iResNet-50 | 约 166 MB | 约 6.3 G FLOPs | 99.80 | 73.85 | 权重非商用 |
| ArcFace R100（Glint360K） | iResNet-100 | 约 248 MB | 约 12.2 G FLOPs | 99.82 | 72.53 | 权重非商用 |
| AdaFace IR-50 | iResNet-50 | 约 166 MB | 约 6.3 G FLOPs | 99.8 级 | 未在同上表 | 代码 MIT；权重需核对 |
| FaceNet（davidsandberg） | Inception-ResNet-v1 | 约 90 MB | 较大 | 99.65 | — | 代码 MIT；权重需核对 |

这张表最重要的信息不是 LFW，而是**东亚人脸一列的差距**：MobileFaceNet 级的轻量模型在东亚人脸上只有 51.03，而 R50 有 73.85。LFW 上两者只差 0.1 个百分点，但在东亚人脸上差了 22.8 个百分点。也就是说，**把模型压到最小，可能在欧美基准上看不出差别，在中国家庭场景却明显掉点。** 原因包括训练数据分布、人脸形态差异、以及轻量模型特征维度不足。

**推荐：**

- MVP：MobileFaceNet 级模型（13 MB、450 M FLOPs），先跑通体验；但必须用真实中国家庭数据校准阈值，并接受“远距离/侧脸更容易拒识”。
- 追求精度：ArcFace R50 蒸馏到 MobileFaceNet，或在 R50 上做 INT8 量化（约 42 MB），旗舰机可跑 20–30 ms。
- 商用：不要直接使用 InsightFace 权重；用公开/授权数据自训，或购买商业授权。

如果目标用户主要是中国家庭，建议把“在自有家庭数据上微调/蒸馏”列为 MVP 后的第一项模型工作。公开的轻量权重在东亚人脸上的表现可能不足；自训/蒸馏至少需要 1–5 万张覆盖不同年龄、光照、角度的授权数据，否则“模型很小但叫错人”的风险会高于“模型稍大但更稳”。

### 5.4.2 特征与匹配

- 输出 512 维 float32，L2 归一化；余弦相似度等价于内积。
- 每人保留 5–10 个模板（不同角度、光照、年份），匹配时取 `max` 或“质心 + max”融合。
- 开集识别：`top1 ≥ T_accept` 且 `top1 - top2 ≥ Δ` 才接受；否则输出候选或“未知”。
- 阈值不是常数：不同模型、不同机型、不同光照分布都不同。建议用 2000 对正负样本校准，取 `FAR = 1e-3` 对应的阈值；常见 ArcFace 类模型落在 0.35–0.50，MobileFaceNet 可能更低。
- 时序融合：同一 track 连续 3 帧命中才显示；track 级取相似度中位数，抑制单帧误判。
- 自适应阈值：按每个人的类内方差调整；底照少的人阈值更高（更容易拒识），底照多的人阈值可略低。

### 5.4.3 家庭场景的个性化校准

家庭规模小（20–200 人），但“长得像”的概率高（父子、姐妹、双胞胎）。可以在端侧做一次轻量校准：

1. 用录入的 5–10 张/人，计算类内相似度分布与类间相似度分布；
2. 对每个人估计一个阈值 `T_i`，使类内召回 ≥ 95%；
3. 匹配时用 `T_i` 与全局阈值取较大者；
4. 用户每次“纠正”后，把纠正样本加入模板（质量合格才加），并重新估计阈值。

这比“再训练一个模型”便宜得多，也更能适应家庭相册的分布。

## 5.5 活体检测：防照片恶作剧即可

活体检测只作为近距模式的可选项，远距不做。

家庭场景的威胁模型很弱：表弟拿手机里的一张照片逗你，或者电视里出现一张脸。不需要金融级活体，但需要避免“对着照片也能叫出称呼”的尴尬。

| 方案 | 体积/算力 | 体验 | 建议 |
| --- | --- | --- | --- |
| 静默活体（MiniFASNet 类） | 约 1.7 MB，单帧 | 无感 | 可选，P2 |
| 动作配合（眨眼/转头） | 无模型 | 打断体验 | 仅在疑似攻击时触发 |
| 深度/红外 | 依赖硬件 | 最好 | 手机不支持，放弃 |
| 不做 | — | 最好 | MVP 可先不做，用“连续多帧 + 3D 姿态变化”粗略过滤 |

建议：MVP 不做专门活体；用“连续 3 帧 + 人脸姿态有微小变化 + 纹理清晰度”做轻量过滤。若后续要防照片，再加静默活体，并明确“非安全级”。

## 5.6 多目标跟踪：让“同一个人”不重复

跟踪在两档都运行；人脸-人体绑定只在近距模式进行，远距只维护 person track。

### 5.6.1 算法选择

| 算法 | 关联方式 | 许可 | 优点 | 缺点 |
| --- | --- | --- | --- | --- |
| ByteTrack | IoU + Kalman，低分框二次关联 | MIT | 简单、快、遮挡鲁棒 | 无外观，长时丢失后难找回 |
| OC-SORT | 观测中心 + 速度方向 | MIT | 非线性运动更好 | 实现稍复杂 |
| BoT-SORT | ByteTrack + 相机运动补偿 + ReID | MIT | 精度高 | 需 ReID 模型，算力高 |
| DeepSORT | Kalman + 深度外观 | **GPL-3.0** | 经典、资料多 | 许可风险；移动端 ReID 重 |

**推荐：ByteTrack。** 家庭聚会场景以室内、慢速、短时遮挡为主，ByteTrack 足够；不需要深度 ReID，省算力也省许可麻烦。

### 5.6.2 移动端实现要点

- 状态向量：`[cx, cy, w, h, vx, vy, vw, vh]`，8 维 Kalman；
- 代价矩阵：`1 - IoU`，Hungarian 求解；20 个 track 时 < 1 ms；
- 两级关联：高分框先关联，低分框再关联（ByteTrack 的核心）；
- 轨迹管理：`NEW → TRACKING → LOST → REMOVED`；LOST 保留 30 帧（约 1 秒），超时删除；
- 人脸-人体绑定：人脸框中心落在人体框内，且 IoU/包含关系满足阈值，则把 face track 绑定到 person track；
- 身份继承：人脸 track 消失后，person track 继续；人脸再次出现时，用 embedding 与历史身份比对，一致则继承，不一致则新建；
- ID 切换抑制：新 track 的第一帧人脸若与某个已知身份高度相似，直接合并，不新建。

### 5.6.3 评测指标

| 指标 | 含义 | 目标 |
| --- | --- | --- |
| MOTA | 检测+关联综合误差 | ≥ 70%（室内） |
| IDF1 | 身份保持 F1 | ≥ 75% |
| IDS | 身份切换次数/分钟 | < 0.5 |
| Frag | 轨迹碎片化次数 | 尽量低 |
| 首帧绑定延迟 | 人进入画面到稳定 ID | ≤ 500 ms |

## 5.7 人脸库与向量检索

家庭规模下，不需要向量数据库：

- 30 人 × 10 模板 = 300 个 512 维向量；
- 一次暴力余弦：300 × 512 ≈ 15 万次乘加，手机 CPU < 0.1 ms；
- 即使 1 万人 × 10 模板 = 10 万向量，约 5000 万次乘加，优化后仍可 < 10 ms。

因此推荐：**Room/SQLite 存 BLOB + 应用层暴力检索**，简单、可控、可加密。ObjectBox 4.x 提供 HNSW 向量检索，可作为规模化备选，但需核对其版本与授权条款。

存储优化：

- embedding 用 float16（1 KB/条）或 int8（512 B/条）+ scale；
- 照片存加密文件，数据库只存路径与哈希；
- 模板表加 `quality`、`created_at`，淘汰低质量/过时模板；
- 删除人时级联删除模板、别名、照片、同意记录。

## 5.8 称呼推理：本产品的“第二大脑”

### 5.8.1 称谓的六个维度

中国亲属称谓不是一张“关系→词”的表，而是六个维度的组合：

| 维度 | 取值 | 例子 |
| --- | --- | --- |
| 血亲/姻亲 | 血亲、姻亲、干亲、继亲 | 伯父 vs 伯母；干爹；继母 |
| 父系/母系 | 父系、母系 | 姑姑 vs 姨妈 |
| 辈分 | +2、+1、0、-1、-2 | 爷爷、爸爸、我、儿子、孙子 |
| 堂/表 | 堂、表 | 堂哥 vs 表哥 |
| 年长/年幼 | 兄/弟、姐/妹 | 伯父 vs 叔叔；大姨 vs 小姨 |
| 排行/地域 | 大伯/二伯；姥姥/外婆 | 二舅、三姨；妗子/舅妈 |

只存一个“称呼”字符串，等于把这六个维度压扁，必然丢失信息。正确做法是存**关系边**，称呼在展示时计算。

### 5.8.2 图模型

- 节点：`person`，包含性别、出生年、排行、是否“我”；
- 边分为三类：`parent`（有向，A → B 表示 A 是 B 的父/母，用 `gender` 区分父/母）、`spouse`（无向，表示婚姻关系）、`sibling`（可由共享父母推导，也可显式存储，用于同父异母/同母异父）。
- 每条边带 `confidence`（用户确认=1.0，规则推断=0.6–0.9）与 `source`（user/inferred）；
- “我”是根节点，称呼是“我 → 目标”的最短关系路径的函数。

### 5.8.3 路径→称呼

`relationship.js` 使用“选择器”表示关系链，例如：

```text
爸爸的哥哥的妻子 → 伯母 / 大娘
妈妈的姐姐 → 姨妈 / 阿姨
爸爸的妹妹的儿子 → 表哥 / 表弟（按年龄）
```

它的核心是一套关系代数：把“爸爸、妈妈、哥哥、姐姐、弟弟、妹妹、丈夫、妻子、儿子、女儿”等原子关系组合成路径，再查表/化简得到称谓。工程上可以：

1. 直接把 `relationship.js` 的词典与规则移植到 Kotlin/Java（MIT，约几百 KB 数据）；
2. 或用 JavaScriptCore/QuickJS 嵌入执行（体积大，不推荐）；
3. 或只移植“路径化简 + 词典”，推理部分自研。

推荐方案 1：把数据与规则抽成 JSON/资源文件，Kotlin 实现查询与化简；这样离线、可测试、可扩展方言。

### 5.8.4 关系图补全规则

用户不可能录入完整家谱。系统需要从已知边推导未知边，但必须标注“推测”，让用户确认。可用的高置信规则：

| 已知 | 推导 | 置信度 | 备注 |
| --- | --- | --- | --- |
| A 是 B 的父亲；A 是 C 的父亲 | B、C 是兄弟姐妹 | 高 | 同母未知，可能是同父异母 |
| A 是 B 的母亲；A 是 C 的母亲 | B、C 是兄弟姐妹 | 高 | 同上 |
| A 是 B 的父亲；C 是 A 的妻子 | C 是 B 的母亲 | 中 | 可能是继母 |
| A 是 B 的兄弟；C 是 A 的父亲 | C 是 B 的父亲 | 中 | 可能是同母异父 |
| A 是 B 的配偶；C 是 A 的父亲 | C 是 B 的岳父/公公 | 高 | 按 B 的性别 |
| A 是 B 的兄弟；C 是 A 的儿子 | C 是 B 的侄子 | 高 | — |
| A 是 B 的姐妹；C 是 A 的儿子 | C 是 B 的外甥 | 高 | — |
| A 是 B 的父亲的兄弟 | A 是 B 的伯/叔 | 高 | 需年龄/排行区分 |
| A 是 B 的母亲的姐妹 | A 是 B 的姨 | 高 | — |
| A 是 B 的父亲的姐妹 | A 是 B 的姑 | 高 | — |

推理策略：

1. 以“我”为根做 BFS，找目标人的最短路径；
2. 路径上每条边若缺失，尝试用规则补全；
3. 补全结果按置信度排序，低置信度不直接显示称呼，显示“可能是……”；
4. 用户确认后，把边写入数据库，置信度置 1.0；
5. 定期做一致性检查（性别冲突、辈分环路、年龄倒挂），提示用户修正。

### 5.8.5 排行与年龄

“大伯/二伯”“大姨/小姨”“堂哥/堂弟”都依赖年龄或排行。数据来源优先级：

1. 用户直接填写出生年/排行；
2. 从关系边推导（如“爸爸的哥哥”天然比爸爸大，但不一定比“我”大）；
3. 未知时，在称呼结果里给“伯/叔”两个候选，或用“叔叔”作为安全默认（北方部分地区对父辈男性通用）；
4. 对同辈，默认“哥/姐”比“弟/妹”更安全（叫大不叫小）。

### 5.8.6 地域变体

| 标准称呼 | 常见变体 | 使用地区（示例） |
| --- | --- | --- |
| 外婆 | 姥姥、阿婆、家婆 | 北方/吴语/粤语 |
| 外公 | 姥爷、阿公 | 北方/粤语 |
| 姑姑 | 姑妈、娘娘、姑姐 | 全国/西北/粤语 |
| 姨妈 | 阿姨、姨姨、姨妈 | 全国 |
| 舅妈 | 舅母、妗子 | 书面/中原 |
| 婶婶 | 婶娘、婶母 | 北方/书面 |
| 伯母 | 大娘、伯娘 | 北方/粤语 |
| 姑父 | 姑丈 | 南方 |
| 姨父 | 姨丈 | 南方 |
| 公公 | 家公 | 粤语/客家 |
| 岳父 | 丈人、老丈人 | 北方口语 |

产品上应允许用户设置“老家/方言偏好”，并在结果里同时给出“标准称呼 + 本地叫法”。遇到不确定的，提供“我们这里叫……”自定义入口，把用户输入作为该人的别名。

### 5.8.7 歧义处理

| 输入 | 歧义 | 处理 |
| --- | --- | --- |
| “阿姨” | 母亲的姐妹；泛称；无亲属关系 | 先问“是妈妈的姐妹吗？”；否则按泛称 |
| “叔叔” | 父亲的弟弟；泛称 | 查关系图；无图则泛称 |
| “表哥” | 父亲的姐妹的儿子；母亲的兄弟/姐妹的儿子 | 要求选择“哪一边” |
| “舅舅” | 母亲的兄弟；也可能指“舅舅的兄弟” | 以“我”为根，只认直系路径 |
| “爷爷” | 父亲的父亲；也可泛称老年男性 | 区分“亲属/尊称”开关 |

对无法确定关系的人，产品应提供“通用尊称”兜底：由用户一键选择“叔叔/阿姨/爷爷/奶奶”，并标注“通用称呼”，而不是自动推断年龄或身份。这也是 App 名字“阿姨你好”的产品含义：先保证不失礼，再追求叫得准。

### 5.8.8 为什么不用大模型做称呼推理

- **确定性**：称呼需要 100% 可解释、可复现，LLM 会幻觉；
- **体积/延迟**：端侧小模型（1–3 B）仍占 1–2 GB，启动/推理慢；
- **数据**：亲属关系是结构化图，规则引擎比 LLM 更擅长；
- **可维护**：方言、排行、政策变化可以用数据更新，不需要重训。

LLM 可以作为“录入时的自然语言解析器”（例如把“这是我爸的二哥”解析成关系链），但必须是可选的、端侧的、并且结果要用户确认。MVP 不需要。

### 5.8.9 一个完整的推理例子

用户说：“这是我爸的二哥，他老婆，还有他们的儿子。”

1. 解析“我爸的二哥” → `F → OB`（爸爸 → 哥哥）→ 创建 person A，关系为 `A sibling-of 爸爸`，且 A 男、年长；
2. 称呼：`F-OB` → “伯父/二伯”（按排行）；
3. “他老婆” → `spouse(A, B)` → `F-OB-W` → “伯母/二伯母”；
4. “他们的儿子” → `parent(A, C)`、`parent(B, C)` → `F-OB-S` → “堂哥/堂弟”（按与“我”的年龄比较）；
5. 图补全：由 `A sibling-of 爸爸` 与 `A parent-of C`，可推出 `C` 与“我”同辈；由 `B spouse-of A` 与 `A parent-of C`，推定 `B` 是 C 的母亲（置信度中，需确认）；
6. 用户确认后，置信度置 1.0，下次直接显示“二伯母”“堂哥”。

这个例子说明：**录入的粒度应该是“关系边”，而不是“称呼字符串”。** 称呼是计算结果，不是存储对象。

# 第6章 数据模型与接口

## 6.1 核心实体

| 实体 | 关键字段 | 说明 |
| --- | --- | --- |
| `person` | id, name, gender, birth_year, birth_order, is_self, avatar, notes | 人；`is_self` 标记“我” |
| `relation` | id, from_id, to_id, type, subtype, confidence, source | 关系边；type=parent/spouse/sibling |
| `face_sample` | id, person_id, image_path, embedding, dim, quality, yaw, blur, created_at | 人脸样本；embedding 存 BLOB |
| `alias` | id, person_id, term, variant, is_primary | 称呼别名/方言叫法 |
| `consent` | id, person_id, scope, granted_by, method, granted_at, revoked_at | 同意记录 |
| `settings` | key, value | 地域、方言、阈值、TTS 等 |
| `audit` | id, action, target, ts | 本地审计（可选） |

关系约束：

- `parent` 有向：`from` 是父/母，`to` 是子女；用 `person.gender` 区分父/母；
- `spouse` 无向：存储时按 `from_id < to_id` 去重；
- `sibling` 可选：默认由共享 `parent` 推导；同父异母/同母异父时显式存储；
- 禁止自环；禁止辈分环路（A 是 B 的父，B 是 A 的父）；
- 删除人时级联删除其关系、样本、别名、同意记录。

## 6.2 SQL 示例

```sql
CREATE TABLE person (
  id           INTEGER PRIMARY KEY,
  name         TEXT NOT NULL,
  gender       TEXT CHECK (gender IN ('M','F','U')) NOT NULL DEFAULT 'U',
  birth_year   INTEGER,
  birth_order  INTEGER,
  is_self      INTEGER NOT NULL DEFAULT 0,
  avatar_path  TEXT,
  notes        TEXT,
  created_at   INTEGER NOT NULL,
  updated_at   INTEGER NOT NULL
);

CREATE TABLE relation (
  id           INTEGER PRIMARY KEY,
  from_id      INTEGER NOT NULL REFERENCES person(id) ON DELETE CASCADE,
  to_id        INTEGER NOT NULL REFERENCES person(id) ON DELETE CASCADE,
  type         TEXT CHECK (type IN ('parent','spouse','sibling')) NOT NULL,
  subtype      TEXT,                -- biological/step/adoptive/elder/younger
  confidence   REAL NOT NULL DEFAULT 1.0,
  source       TEXT NOT NULL DEFAULT 'user',
  created_at   INTEGER NOT NULL,
  UNIQUE (from_id, to_id, type)
);

CREATE TABLE face_sample (
  id           INTEGER PRIMARY KEY,
  person_id    INTEGER NOT NULL REFERENCES person(id) ON DELETE CASCADE,
  image_path   TEXT NOT NULL,
  embedding    BLOB NOT NULL,
  dim          INTEGER NOT NULL DEFAULT 512,
  quality      REAL NOT NULL DEFAULT 0,
  yaw          REAL,
  blur         REAL,
  created_at   INTEGER NOT NULL
);

CREATE INDEX idx_relation_from ON relation(from_id);
CREATE INDEX idx_relation_to   ON relation(to_id);
CREATE INDEX idx_sample_person ON face_sample(person_id);
```

## 6.4 导入导出与家族共建

- **导出包**：ZIP + AES-GCM；内容为 `manifest.json`（schema 版本）、`persons.json`、`relations.json`、`aliases.json`、`photos/`；
- **二维码**：只传关系图（不含照片/embedding），压缩 JSON，适合“扫一下把家谱发给表姐”；
- **合并策略**：以 UUID 为主键；同名/同脸冲突时让用户选择“合并/新建”，绝不自动合并人脸；
- **权限**：导出需要二次确认 + 应用锁；导入需要展示“将写入多少人、多少照片”；
- **冲突**：关系边冲突（A 是 B 的父 vs A 是 B 的叔）不自动覆盖，标记为“待确认”。

## 6.5 数据生命周期

| 阶段 | 动作 | 说明 |
| --- | --- | --- |
| 采集 | 相机/相册 → 质量筛选 | 原始帧用完即丢，不落盘 |
| 录入 | 对齐 → embedding → 加密存储 | 照片加密，embedding 入 SQLCipher |
| 使用 | 匹配 → 显示 → 可选播报 | 全程本地，无网络请求 |
| 纠正 | 用户改称呼/关系 | 写别名/边，更新置信度 |
| 撤回 | 用户撤销同意 | 删除该人样本、embedding、别名 |
| 删除 | 删除人/清空数据 | 级联删除；提示“不可恢复” |
| 备份 | 加密导出 | 不启用系统自动备份 |
| 审计 | 记录关键操作 | 可选，本地保存，不上传 |

> **工程提醒：** Android 的 `allowBackup` 必须设为 `false`，否则人脸库可能被系统自动备份到云端，直接违反“本地存储”的设计承诺。照片目录要放在应用私有目录，不要放 `DCIM` 或公共相册。
