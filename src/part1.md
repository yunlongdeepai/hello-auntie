# 摘要

“阿姨你好”要解决的是一个高度具体、但技术链条很长的场景：过年回家，面对一屋子似曾相识的亲戚，用户希望手机在完全离线的情况下，先发现人、再认出人、最后给出正确的称呼，并且能在已知部分亲戚关系的前提下，继续推导出其他亲戚该怎么叫。

本报告按最新约束展开：**远距只做检测 + 跟踪、不跑人脸；近距才做人脸识别**；平台**只适配 ColorOS 14–17**，其他 Android 暂不适配。

本报告的核心判断是：**人脸识别只完成了“这是谁”，而用户要的是“我该叫他什么”。** 后者取决于“我”与对方在亲属网络中的路径、辈分、排行、地域习惯，甚至对方与我的年龄差。因此系统必须是“感知 + 关系推理”的双引擎，而不是一个换皮的人脸识别 App。把问题简单理解为“目标检测 + 跟踪 + 人脸识别 + 数据库”，会漏掉两个决定成败的模块：**亲属关系图/称呼推理**与**低负担的录入校准**。

## 结论速览

| 维度 | 结论 |
| --- | --- |
| 技术可行性 | 可行。端侧人脸检测、特征提取、人体检测、多目标跟踪均有成熟开源方案；中端 ColorOS 手机可做到远距 25–30 FPS、近距 15–20 FPS。 |
| 真正的难点 | 不是模型，而是三件事：① 称呼依赖“我”的关系图，不能只靠人脸；② 新用户冷启动录入 20–50 位亲戚的负担；③ 远距离下人脸像素不足，识别距离有物理上限。 |
| 推荐主线 | CameraX + LiteRT + EfficientDet-Lite0（人体）+ SCRFD-2.5G（人脸）+ MobileFaceNet（特征）+ ByteTrack（跟踪）+ Room/SQLCipher（本地库）+ relationship.js 移植（称呼推理）。 |
| 适配范围 | 仅 ColorOS 14–17（对应 Android 14–17，API 34–37），以 OPPO 机型为准；一加/真我对应版本需逐机型确认；其他 Android 暂不适配。 |
| 远近策略 | 远距（约 4 m 以外）只做人体检测 + 跟踪，不加载人脸模型；近距（约 ≤4 m）才做人脸检测与识别（2–3 m 稳定，4 m 候选）。 |
| 合规底线 | 人脸信息默认只存本机、不上传；单独同意；不满 14 周岁取得监护人同意；可撤回、可删除；做个人信息保护影响评估；不把人脸作为唯一验证方式。 |
| 许可证风险 | Ultralytics YOLO 为 AGPL-3.0，闭源商用需企业授权；InsightFace 模型权重“仅限非商业研究”；DeepSORT 为 GPL-3.0。三者是开源复用清单里最容易踩的坑。 |
| 实施建议 | 2–3 人、10–12 周可完成可内测的 MVP；先用 20–30 人的真实家庭聚会数据校准阈值，再谈规模化。预算约 30–60 万元（自研人力口径），模型商用授权另计。 |

> **一句话建议：** 先做“关系图 + 称呼推理 + 低负担录入”，再把人脸识别接进来；不要反过来。前者决定产品是否成立，后者决定体验是否顺滑。

# 第1章 项目背景与需求定义

## 1.1 场景与痛点

春节走亲访友是一个高频、集中、强社交压力的场景。用户真正紧张的时刻通常只有三个：

1. **门口迎接**：长辈从屋里迎出来，距离 2–5 m，用户需要在 1–2 秒内叫出正确称呼，否则气氛立刻尴尬。
2. **饭桌介绍**：一桌十几个人，父母逐一介绍“这是你爸的表哥”“这是你三姨”，信息密度极高，饭后基本忘光。
3. **路上偶遇**：在村口或小区遇到“看着眼熟”的亲戚，既不能装作没看见，又想不起该怎么叫。

不同人群的痛点并不相同：

| 人群 | 典型困境 | 对产品的期待 |
| --- | --- | --- |
| 返乡青年 | 一年见一次，只记得脸不记得称呼 | 抬起手机就能看到名字/称呼，最好能语音提示 |
| 新媳妇、新女婿 | 对配偶家的亲戚网络完全陌生 | 按“老公的舅舅”“婆婆的姐姐”这种路径也能算出来 |
| 儿童、青少年 | 被要求“快叫人”，但不知道怎么叫 | 大字号、卡通化、即时提示 |
| 长辈 | 记得住人，但记不住辈分和排行 | 能自己录入、能纠正、能分享给子女 |
| 社恐人群 | 不想当众问“我该叫您什么” | 低调、快速、不引人注意的查询方式 |

痛点背后有一个容易被忽略的事实：**“叫错”比“叫不出”更严重。** 叫不出可以含糊过去，叫错（把姑姑叫成姨妈、把堂哥叫成表哥）会被认为“不懂事”。因此产品不能只给一个高置信度答案，还要在不确定时给出候选、允许快速纠正，并明确区分“亲属称呼”和“通用尊称”。

## 1.2 现有解决方式及其局限

| 方式 | 做法 | 局限 |
| --- | --- | --- |
| 问父母 | 现场小声问，或提前微信问 | 当众问显得不礼貌；父母也未必记得清远房关系 |
| 称呼计算器 | 在小程序/网页里输入“爸爸的哥哥” | 需要先知道关系链，且完全靠手动输入，不能识脸 |
| 相册人脸分组 | 用手机相册或 NAS 的人脸聚类 | 只能把照片分组，不能给出称呼，也不能实时提示 |
| 硬背 | 过年前列清单、看照片 | 准备成本高，临场容易忘 |
| 智能门锁/门禁 | 1:N 人脸识别开门 | 只解决“是不是这个人”，不解决“该怎么叫” |
| AI 眼镜 | 实时显示姓名/信息 | 依赖云端、续航短、隐私争议大、价格高 |

这些方案各自解决了问题的一段，但没有一个把“看见人 → 认出人 → 推出称呼 → 告诉我”串成闭环。尤其是“推出称呼”这一步，几乎被所有现有人脸产品忽略。

## 1.3 功能需求拆解

把用户设想翻译成可验收的需求（新增平台范围约束）：

| 编号 | 需求 | 说明 | 优先级 |
| --- | --- | --- | --- |
| R1 | 实时识脸出称呼 | 相机对准人脸，叠加显示称呼；置信度不足时显示候选 | P0 |
| R2 | 照片/相机录入 | 支持相册选照、现场拍摄，录入姓名、称呼、关系链 | P0 |
| R3 | 远距离模式 | 只运行人体检测 + 多目标跟踪，不加载人脸检测/识别模型；界面显示“有人/目标” | P0 |
| R4 | 近距离模式 | 人体检测 + 跟踪 + 人脸检测 + 对齐/质量 + 1:N 识别 + 称呼 | P0 |
| R5 | 同一目标跟踪 | 目标移动、短暂遮挡后保持同一 ID，不重复弹出 | P1 |
| R6 | 本地人脸库 | 人脸特征、照片、关系数据全部离线存储 | P0 |
| R7 | 关系推理 | 由已知关系推导未知亲戚的称呼（如“爸爸的哥哥的妻子”） | P0 |
| R8 | 编辑与纠正 | 称呼、关系、照片可随时修改；支持“我们这里叫……” | P0 |
| R9 | 家族共建/迁移 | 换机、多人协作录入、加密导出导入 | P2 |
| R10 | 平台范围 | 仅适配 ColorOS 14–17；其他 Android 系统暂不适配 | P0 |

其中 R7（关系推理）是本产品与普通人脸识别工具的分水岭。它意味着数据模型不能只存“张三 = 三姨”，而要存“张三与‘我’的关系路径”，否则换一个人使用、或者关系变化（结婚、离婚、长辈去世）时，称呼就无法自动更新。

## 1.4 非功能需求

| 类别 | 要求 | 验收口径（建议） |
| --- | --- | --- |
| 离线 | 所有推理在本机完成，飞行模式可用 | 断网、关定位、关蓝牙下完整走通 |
| 实时 | 预览到标注的端到端延迟 | 中端机 p95 ≤ 150 ms；识别结果 3 帧内稳定 |
| 准确 | 家庭规模下的开集识别 | 30 人、每人 5 张底照，rank-1 ≥ 95%，误认率 ≤ 1% |
| 隐私 | 人脸数据不出设备 | 抓包无任何人脸/特征外传；默认关闭云同步 |
| 兼容 | 只覆盖 ColorOS 14–17 | Android 14–17（API 34–37），arm64-v8a，6 GB RAM 起；OPPO/一加/真我对应版本；其他 Android 暂不适配 |
| 体积 | 首次安装包尽量小 | 基础包 ≤ 60 MB；模型可按需下载 |
| 功耗 | 连续使用不烫手 | 10 分钟温升 ≤ 8 °C；电量消耗 ≤ 15% |
| 易用 | 录入 1 人 ≤ 60 秒 | 3 张照片起录，质量不合格即时提示 |

## 1.5 产品边界

明确“不做什么”，比“做什么”更能控制风险：

- **不做安防/监控**：不面向公共场所、不做陌生人身份识别、不做后台静默采集。
- **不做身份认证**：不用于门禁、支付、考勤，不宣称“金融级活体”。
- **不做云端**：不上传人脸、不调用云端 API、不依赖网络。
- **不做社交**：不做家族广场、不做公开排行，避免把亲属关系变成可爬取的数据。
- **平台边界**：只适配 ColorOS 14–17；不承诺原生 Android、其他 ROM、HarmonyOS NEXT。
- **不追求“认识所有人”**：只服务用户自己录入的亲属圈；陌生人一律显示“未知”，不猜身份。

## 1.6 三个关键洞察

**洞察一：称呼 = 身份 × 关系路径 × 排行 × 地域。**

同一个人，对不同的人有不同的称呼：她是“我”的三姨，却是“我妈妈”的妹妹、我表弟的“三姑”。如果数据库里只存一个字符串“三姨”，换一个使用者就会全错。正确做法是存“人”和“关系边”，称呼在渲染时按“当前用户（ego）→ 目标人”的路径实时计算。

**洞察二：冷启动是最大的产品风险，不是算法风险。**

一个家庭聚会 30 人，如果每人要拍 10 张照片、填 4 个字段，总录入时间超过 1 小时，用户会在第一次使用时就放弃。必须把录入压缩到“3 张照片 + 1 个关系链选择”，并提供家族共建、批量相册导入、语音/文字解析等加速手段。

**洞察三：错误成本不对称，产品必须“可拒识、可候选、可纠正”。**

宁可显示“这位是……（不确定）”并给出 2–3 个候选，也不要自信地叫错。开集识别、阈值保守、候选列表、单击纠正，是比“再训一个更大的模型”更有效的体验设计。

## 1.7 调研方法与范围

本报告采用四种方法：

1. **公开资料与论文调研**：法规原文、Android/Google AI Edge 官方文档、人脸识别与多目标跟踪的代表性论文；
2. **开源仓库许可证核查**：对计划复用的项目逐一核对代码 LICENSE、模型权重声明与数据集限制；
3. **公开基准对比**：引用 InsightFace 模型库、WIDER FACE、LFW 等公开数据，做相对比较，不把公开基准当作家庭场景的绝对准确率；
4. **工程测算**：按目标机型的算力、相机光学参数、模型 FLOPs 做延迟与距离估算，并明确标注“估算”。

本报告**未开展**大规模用户访谈、ColorOS 14–17 全机型真机 benchmark 和长期家庭场景跟踪测试；文中标注为“估算/参考值”的数字，需要在立项后 2 周内用目标机型与真实家庭数据复核。法规与许可证信息以 2026 年 11 月可访问的公开版本为准，上线前应再次核对。

# 第2章 市场与竞品调研

## 2.1 称呼计算器类工具

这是最接近“称呼”需求的一类产品，形态包括微信小程序、网页工具和独立 App。其典型交互是：用户选择“爸爸 → 哥哥 → 妻子”，工具输出“伯母/大娘”。这类产品背后很多使用了开源的 `relationship.js`（MIT 协议，GitHub 约 3.7k stars，持续维护到 2026 年），它把中国亲属称谓做成了可计算的关系代数。

优点：

- 称呼覆盖广，能处理堂/表、姻亲、辈分、排行等复杂规则；
- 纯前端、体积小、离线可用；
- 已有大量现成的称谓数据，可直接复用。

局限：

- **必须先知道关系链**。用户如果连“他是谁的谁”都不知道，工具就无从算起；
- 没有视觉入口，不能识脸，不能实时提示；
- 交互是“查词典”，不是“见人叫人”；
- 对方言/地域变体支持有限，通常只给一个标准答案。

这类产品证明了“称呼可以被算法化”，但没有解决“如何知道对方是谁”。

## 2.2 人脸相册与人脸识别类产品

手机相册（Google Photos、小米相册、华为图库）、NAS 相册（群晖 Photos、极空间）普遍具备人脸聚类能力：把同一个人的照片聚成一组，让用户命名。它们的优势是数据量大、聚类成熟；局限是：

- 只做“分组 + 姓名”，不做“称呼”；
- 大多在云端或 NAS 上算，不符合“全部本机算力”的要求；
- 不能实时预览，不能回答“现在面前这个人是谁”；
- 对老人、儿童、跨年份照片的聚类效果会下降。

门禁/门锁类产品做的是 1:N 白名单识别，只关心“是否允许通行”，不关心亲属关系；AI 眼镜类产品能实时显示信息，但普遍依赖云端、续航短、价格高，且“对着人扫描”的社交接受度低。

## 2.3 竞品对比

| 能力 | 称呼计算器 | 相册人脸分组 | 门禁/门锁 | AI 眼镜 | 本产品目标 |
| --- | --- | --- | --- | --- | --- |
| 实时识脸 | 否 | 否 | 是 | 是 | 是 |
| 输出称呼 | 是（需手输关系） | 否 | 否 | 部分 | 是 |
| 关系推理 | 是 | 否 | 否 | 否 | 是 |
| 离线 | 是 | 部分 | 是 | 否 | 是 |
| 远距离发现 | 否 | 否 | 部分 | 是 | 是 |
| 目标跟踪 | 否 | 否 | 部分 | 是 | 是 |
| 隐私风险 | 低 | 中 | 中 | 高 | 低（本地） |
| 使用门槛 | 中 | 低 | 低 | 高 | 中 |

## 2.4 市场空白与机会

市场的空白不在于“再做一个称呼计算器”，也不在于“再做一个相册聚类”，而在于：

1. **把视觉身份和亲属关系连起来**：看到人 → 认出人 → 按“我”的关系图算称呼；
2. **把“查”变成“提示”**：不需要用户先输入关系链，而是在相机预览里直接标注；
3. **把“标准答案”变成“我家的答案”**：支持地域变体、排行、自定义叫法；
4. **把“云端识别”变成“本机识别”**：解决隐私顾虑，也解决农村/山区网络差的问题。

差异化可以概括为一句话：**“别人做的是人脸识别，我们做的是见人称呼。”**

# 第3章 技术可行性总览

## 3.1 端侧算力现状

2023 年以后的中高端安卓手机，普遍具备可用的端侧 AI 算力：

- **CPU**：ARM big.LITTLE，8 核；INT8 推理可用，但能效一般；
- **GPU**：Adreno / Mali / Immortalis，适合卷积网络，LiteRT GPU delegate、MNN、NCNN 均可利用；
- **NPU**：高通 Hexagon、联发科 APU；峰值算力从几 TOPS 到几十 TOPS，但需要通过厂商 SDK（QNN、NeuroPilot）或 LiteRT 的厂商后端调用，碎片化明显；
- **运行时生态**：Android 15 起 NNAPI 被标记为废弃，Google 建议迁移到 LiteRT GPU delegate 或厂商 SDK；新项目不应把 NNAPI 作为主路径；
- **内存**：8–16 GB 常见，但留给 App 的常驻内存仍应控制在 200–300 MB 以内；
- **热约束**：持续推理 5–10 分钟后普遍降频，必须做帧率自适应。

一个重要的工程事实：**峰值算力不等于持续算力。** 发布会上说的 30 TOPS 是短时峰值；家庭聚会场景通常要连续使用 10–30 分钟，真正可依赖的是“中端机 15–20 FPS、高端机 25–30 FPS”的持续水平。

## 3.2 先算清楚“能看多远”：光学与分辨率上限

在讨论模型之前，必须先算物理上限。假设主摄等效 26 mm、水平视场角约 60°、输出 1920×1080：

- 焦距像素数 `f_px = 1920 / (2 × tan(30°)) ≈ 1663 px`；
- 人脸宽度按 0.15 m 计，人脸像素宽 `w ≈ 1663 × 0.15 / d = 249 / d`；
- 人体高度按 1.7 m 计，人体像素高 `h ≈ 1663 × 1.7 / d = 2828 / d`。

| 距离 d | 人脸像素宽（1080p） | 人体像素高（1080p） | 本产品模式 |
| --- | --- | --- | --- |
| 1 m | 249 px | 2828 px | 近距：识别 + 活体 |
| 2 m | 125 px | 1414 px | 近距：稳定识别 |
| 3 m | 83 px | 943 px | 近距：识别临界（≥80 px） |
| 4 m | 62 px | 707 px | 近距：候选/不稳定（≥60 px） |
| 5 m | 50 px | 566 px | 远距：只检测 + 跟踪 |
| 8 m | 31 px | 354 px | 远距：只检测 + 跟踪 |
| 10 m | 25 px | 283 px | 远距：只检测 + 跟踪 |
| 20 m | 12 px | 141 px | 远距：人体检测 |
| 30 m | 8 px | 94 px | 远距：小目标检测 |

结论：

- **人脸识别是瓶颈，不是人体检测。** 1080p 下，人脸宽 ≥80 px 约在 3 m、≥60 px 约在 4 m；因此近距模式建议在 ≤4 m 开启，稳定识别 2–3 m。2× 光学变焦可以把有效焦距翻倍，稳定识别扩展到 4–6 m，8 m 只能出候选。
- **数码变焦不增加信息。** 把 2 m 处的人脸放大到 4 m 处，只是插值，不会提升识别率；真正有效的是光学长焦、更大的传感器、更高的分辨率。
- 因此产品把能力拆成两档：**远距模式只发现并跟踪“有人”，近距模式才识别人脸、输出称呼。** 这也是两档状态机存在的物理依据。

> **产品含义：** 宣传语不要写“10 米识人”。写“远距离先发现，走近自动认出”，既准确，也不会制造无法兑现的预期。

## 3.4 三条技术路线对比

| 维度 | 路线 A：全 MediaPipe/ML Kit | 路线 B：LiteRT + 专用模型（推荐） | 路线 C：NCNN/MNN 自研 |
| --- | --- | --- | --- |
| 组成 | MediaPipe Face Detector + ML Kit + CameraX | LiteRT + EfficientDet-Lite0 + SCRFD + MobileFaceNet + ByteTrack | NCNN/MNN + 自选模型 + 自研前后处理 |
| 开发周期 | 最短（2–4 周出 Demo） | 中（6–8 周出 MVP） | 长（10–16 周） |
| 识别能力 | 无人脸特征 API，需要另接模型 | 完整可控 | 完整可控 |
| 小脸/远距 | 一般（BlazeFace 为主） | 好（SCRFD） | 好 |
| 性能 | 好 | 好 | 最好（可深度定制） |
| 机型兼容 | ML Kit 部分能力依赖 GMS，国内 ColorOS 可能不可用 | 纯本地库，ColorOS 14–17 可控 | 纯本地库，需自行适配 |
| 许可风险 | 低（Apache/Google 条款） | 取决于模型权重 | 取决于模型权重 |
| 适用 | 快速验证、Demo | 大多数团队的产品化首选 | 有 CV 基建、追求极致性能 |

**推荐路线 B。** 理由：

1. MediaPipe/ML Kit 没有人脸特征提取（embedding）能力，最终仍要接一个识别模型；既然要接，不如一开始就把检测、识别、跟踪都放在 LiteRT 管线上，减少“两套前后处理”的维护成本。
2. 国内 ColorOS 通常不带 GMS，ML Kit 的部分能力不可用；只适配 ColorOS 时，应该把检测/识别全部放在本地 LiteRT 管线上，避免 GMS 依赖。
3. LiteRT 是 Android 官方路线（原 TensorFlow Lite，2024 年更名），GPU delegate 成熟，社区资料多；后续要换 NCNN/MNN 也有迁移空间。

## 3.5 可行性结论

- **推荐配置（MVP）**：CameraX + EfficientDet-Lite0 + ByteTrack + SCRFD-2.5G + MobileFaceNet + Room/SQLCipher + relationship.js 移植（详见第 7 章复用清单与第 11 章 MVP 范围）；平台只适配 ColorOS 14–17（Android 14–17）。

综合评估：

- **算法可行**：核心模块均有成熟开源实现或公开模型，无需从零训练检测器。
- **性能可行**：中端机 15–20 FPS、端到端 100 ms 是合理目标。
- **工程可控**：工作量主要在跟踪、身份融合、关系推理与录入体验。
- **风险可控**：许可证、隐私、远距预期、冷启动需提前处理。
- **平台聚焦可行**：只适配 ColorOS 14–17，可把机型矩阵从“全安卓”收敛到 4 个系统大版本，测试与优化成本显著下降；代价是用户覆盖变窄。
